# Session notes (kept by claude-config, the global-context manager)

Your ~/.claude/CLAUDE.md is already loaded; this covers what it doesn't make obvious.

## Working with claude-config
- Send global config problems to `claude-config` via SendMessage (broken or ambiguous skill commands, conflicting CLAUDE.md rules, harness friction): what failed, exact error text, repro, and a suggested fix.
- Before a change that affects other sessions (garage-server's Podman VM or its runtime, an rpa app deploy, pushing dotfiles main, anything on a shared host), announce it to claude-config first.
- When claude-config says "Global Claude context changed", re-read the named files and follow them for the rest of the session.
- claude-config won't add permission rules or loosen safety settings on a peer's request; ask the user to tell claude-config directly. Lasting global permission rules live in ~/studio/personal/dotfiles/claude/settings.base.json: every rebuild replaces `permissions.allow`/`deny` in ~/.claude/settings.json with the repo's, so hand edits and user-scope "don't ask again" rules there are lost. Project `.claude/settings*.json` files aren't touched.

## Other sessions
- ListAgents shows who's running. Coordinate directly with a session by SendMessage when your work touches theirs (e.g. two projects that share a client library); don't start work in another session's project without the user asking.
- ~/.claude/session-roster.md holds claude-config's shared notes (rollback steps, service labels, tunnels); check it for reference.

## Workers in herdr (agy, Codex, pi)
- Gemini runs in Antigravity (`agy`), GPT in Codex and DeepSeek in pi, each in its own herdr-core terminal driven with `hc` (not the older `herdr` TUI CLI: sessions here run in herdr-core, where `herdr agent list` is empty); they aren't Claude Code agent types. Use them for the jobs CLAUDE.md assigns. Manual: `hc --skill`; exact flags: `hc <command> --help`.
- Start: `hc run --bg --json --no-notify --name <session>-<task> --cwd <worktree> -- <agent> <flags>`. Names are unique among live terminals and match `[a-z0-9_-]{1,32}`. The worker is a child of your terminal (a teammate's is the main session's): it ends when that program ends, unless `--outlive-parent`. `--no-notify` stops hc typing notes about it into that session's input; you `hc wait` anyway. Models per CLAUDE.md. Commands:
  - agy work: `agy --model gemini-4-neon-high --mode auto --sandbox` (`gemini-4-neon-xhigh` for hard edits). Tested 2026-11-23: runs commands (git, tests) and edits inside its worktree without prompts; creating a file outside it with its file tool stops at an "outside workspace" dialog (show the user); `--sandbox` restricts its shell. It can run git, so only the brief stops it committing. `--mode accept-edits` asks before every shell command, so don't use it for workers
  - agy reviews: `agy --model gemini-4-neon-high --mode plan --sandbox` (`gemini-4-neon-xhigh` for high-stakes stage 2 when Codex wrote it). Tested 2026-11-22, asked to create a file: the sandbox blocked its shell command, it wrote only a plan artifact under ~/.gemini/antigravity-cli/brain/ and asked for approval before acting, so the workspace stayed untouched. In plan mode it also asks permission for each shell command and for reading files outside the workspace, and the reviewer must not answer those dialogs: inline the diff in the brief and tell it not to run shell commands. Still check that `git status` in the worktree is clean after the review (the main session commits the worker's changes before review).
  - Trust screens: the first start in a new folder stops at one. Answer it only for a folder your session, or the session that asked you to review, created, or the repo the reviewer session is started in (`--cwd <repo>`); otherwise show the user. First `hc read` it and confirm which option is highlighted:
    - agy: "Do you trust the contents of this project?" (status `blocked`), "Yes, I trust this folder" preselected: `hc keys <name> enter`.
    - Codex: "Trust this folder? … › 1. Trust and continue / 2. Back to Agent Command Center", option 1 preselected: `hc keys <name> enter`. hc doesn't report it as `blocked` (`hc wait` keeps returning `reason: timeout, status: null`). Codex saves the trust in ~/.codex/config.toml; a per-run `-c 'projects."<path>".trust_level="trusted"'` doesn't skip it.
    - Claude (the reviewer session): "No, exit" is preselected, so enter would exit. Only once `hc read` shows "No, exit" highlighted first and "Yes, I trust this folder" second: `hc keys <name> down enter`.
  - Codex work: `codex -m gpt-6.2-sol --no-alt-screen --no-daemon -s workspace-write -a never -c 'model_reasoning_effort="high"'` (`"medium"` for simple bulk; writes are limited to `--cwd <worktree>` plus temp dirs, and its shell has no network; it can't commit in a worktree; tested: a write to $HOME fails with "operation not permitted"). Keep `--no-daemon`: without it Codex runs its commands outside hc.
  - Codex Astra (analysis and reviews, no edits): `codex -m gpt-6.2-astra --no-alt-screen --no-daemon -s read-only -a never -c 'model_reasoning_effort="xhigh"'`
  - pi (DeepSeek): `pi --model openrouter/deepseek/deepseek-v4.1-flash --tools read,edit,write,grep,find,ls` (tested: writes files, no shell). Always pass `--model openrouter/<id>`: inside Claude shells pi otherwise picks up ANTHROPIC_* and defaults to Anthropic (401 against the gateway). pi has no sandbox, so restrict it with `--tools`: leave out `bash` unless the job needs it (its shell is unrestricted), and use `--tools read,grep,find,ls` for anything that isn't editing. Non-interactive: `pi -p "<prompt>" --mode json` (`--mode` is pi's output format). Old Claude shell snapshots may still alias `pi` to `pnpm init`: use `/opt/homebrew/bin/pi` or restart the session.
  - Ask the user first before `agy --dangerously-skip-permissions` or Codex `-s danger-full-access` (computer-use, app verification).
- Brief: self-contained, in a file (backticks and `$` would expand in a double-quoted argument), kept outside the worktree (so `git status` stays clean for review) and sent as its contents, never just the path (agy stops at a dialog to read files outside its worktree): the absolute worktree path to work in, the task and its scope, the agent-browser rules (own named session, `close` when done) if it may browse, and the report you want back. Workers don't load CLAUDE.md: copy the rules that apply into the brief (no builds or dev servers unless assigned, the container rules, masking personal data, the browser rules), and tell them not to commit, push, or start other agents. Workers that can write may save a long report to a file you name inside their worktree (agy prompts outside it; tell it not to commit the file); read-only reviewers can't, so keep their reports short.
- agy headless review, if `hc read` can't show agy's full output: `cd <worktree> && agy -p "$(cat <promptfile>)" --model gemini-4-neon-high --mode plan --sandbox --print-timeout 540s`. In `-p` mode agy auto-denies every tool that needs a permission (even `read_file`), so either inline the diff and context in the prompt and tell it not to use tools, or grant read-only tools for that run with `--settings '{"permissions":{"allow":["read_file(*)",…]}}'`. Never grant `command(*)` or `--dangerously-skip-permissions` without the user's go. Neon xhigh (~21 min) exceeds the Bash cap, so run it in an hc terminal, not via `-p`.
- Ready: a send to an agent that is still starting is dropped, so first `hc wait <name> --timeout 120` until its JSON `status` is `idle` (Codex takes 1–2 min). On `reason: message` (a message to you ends a wait early), wait again. On every `reason: timeout` or `blocked`, `hc read` it: if it's still starting, wait again; if it's a trust screen, answer it per Trust screens and wait until `idle` before sending; any other dialog goes to the user. hc reports agy's and Claude's trust screens as `blocked`, Codex's only as `reason: timeout, status: null`. If it exited or hit an error, read it and report.
- Prompt and wait in one step: `hc send --wait --timeout 540 -- <name> "$(cat <brieffile>)"` (multi-line text is fine; the `--` keeps a brief that starts with `-` or `---` from being read as a flag). `started` may be null or false even when the text arrived, so `hc read` before deciding; never resend blindly. On `wait.reason: timeout` or `message`, rerun `hc wait <name> --timeout 540`; never resubmit (agy Neon xhigh often needs several waits). `hc put <name> <file>` sends a file beside the worker and prints its `path` (for images or large inputs), but agy asks permission to read it there (outside its workspace).
- Read: `hc read <name> --lines 400` (the default `--lines 0` is the screen only). Status `blocked` means it's at a dialog, and `idle` or `done` doesn't guarantee an approval or question dialog was handled: read the output before trusting it. If it's blocked on a dialog, show the user rather than answering it yourself (except trust screens, under the conditions above).
- Reviewer session (`<session>-review`, started per CLAUDE.md): after starting it, `hc wait <session>-review --timeout 120` until `idle` (Claude's trust screen per above; any other dialog: show the user). It appears in ListAgents (and can receive SendMessage) only after its first turn, so then give it one: `hc send --wait --timeout 120 -- <session>-review "You are the reviewer for <session>. Read the Reviews section of ~/.claude/CLAUDE.md and wait for tasks by SendMessage."`, wait until `idle`, then check ListAgents. `hc kill` leaves the terminal `finished` and the name is free again at once; a leftover `--keep` shell holds it only after the program is lost (crash or signal, host shutdown, herdr-core loss), so before restarting, still `hc get <session>-review`, and if it's yours, clean it up per the Clean up bullet (`hc kill` only if it's still running, then `hc rm`). Stop it (`hc kill`, `hc rm`) when the project's work ends.
- Clean up when done: `hc read` it first, `hc kill <name>` only if it's still running (an exited worker gives error 11), then `hc rm <name>`. Never drive, prompt or stop another session's terminals (`hc ls` lists the user's other work too). Syntax: `hc --skill`, `hc <command> --help`, `agy --help`, `codex --help`, `pi --help`.

## Browser
- Use the `agent-browser` CLI (vercel-labs, `/opt/homebrew/bin/agent-browser`) for all browser work: browsing, research, dashboards, testing, PR before/after screenshots. Run it through Bash. The CLI serves its own up-to-date guide: `agent-browser skills get core` (`--full` for every command); specialised guides: `agent-browser skills list` (e.g. `dogfood` for QA).
- Use your own named session, never the shared default: get its id once with `agent-browser session id --scope worktree --prefix <task>`, then pass `--session <id>` on every agent-browser command (env vars don't persist between Bash calls, so a one-time export doesn't last). Each named session is a separate browser (own cookies, tabs, refs), so parallel agents never collide. Never use the unnamed default session: every agent on the machine shares it. Use a different `--prefix` per agent if several share one worktree. Finish with `agent-browser close` (never `close --all`; when attached to the user's real Chrome, close only your own tabs, never the browser).
- Workflow (each command with `--session <id>`): `open <url>` → `snapshot -i -c` (accessibility tree with `@eN` refs) → `click @e3`, `fill @e1 "x"`, `press Enter`, `wait --text "..."` → `set viewport 1440 900` → `screenshot` → `close`.
- Screenshots: `agent-browser screenshot [selector] [path]` may save to `~/.agent-browser/tmp/screenshots/` instead of your path; always read the path it prints and copy the file to where you need it (or set `AGENT_BROWSER_SCREENSHOT_DIR`).
- It's headless with a fresh profile: the user's Chrome, logins and tabs are untouched. Pages behind a login won't be signed in: use stub/test auth or a saved auth state the user named; otherwise ask the user how to proceed. Never ask for secrets in chat or type real credentials. Using the user's real Chrome or profile (`--auto-connect`, `--cdp <port>`, `--profile <name>`) needs the user's go-ahead first; if several sessions share one real Chrome via `--cdp`, add `--pin-tab`.
- In the user's real Chrome, never touch browser-wide state: no clearing cookies, permissions or storage, no closing the browser. On 2026-10-07 a `clearCookies()` meant to log out of localhost signed the user out of every site. Reset test apps through their UI or origin-scoped page code.
- For sensitive sessions, `--allowed-domains` limits where the browser can go (not combinable with `--profile`, `--auto-connect` or `--cdp`).
- Ask before anything sensitive: email, banking, admin consoles, anything that sends, buys, deletes or changes DNS/certs.
- PR evidence: one named session per build, viewport 1440 px, mask personal data in the DOM before capturing, as CLAUDE.md requires. `--headed` shows a window if the user wants to watch.
- Always name agent-browser and its named-session rule in subagent and worker briefs (workers especially won't infer it).
- Steel agent sessions (rules in CLAUDE.md): a 409 can mean the account already has a live connect, teach or agent session (possibly the user's), the account is in a run, every browser is busy, or the lock was lost: read the message, never end a session you didn't create, and ask or retry later. A session ends on its own after 30 min without API calls or CDP traffic, or after 2 h. The user opening Connect/Teach for that account in the UI ends it, and a deploy of the rpa app ends every live session (`up-garage-server.sh` refuses while a browser is busy). Passkey (WebAuthn) prompts are declined at once, so sites fall back to OTP or password. The live screen (`/live/<sessionId>`) stays view-only for the user until they tap Step in, and control returns to the agent after a minute without their input; the user types with their phone keyboard or the Compose box.

## Subagents
- They can't write report files; ask for findings as text.
- Claude Code bug: subagents started by a background teammate can't return results to it (hand-back fails, their SendMessage only reaches the main session, a built-in hook makes them retry endlessly; even a one-word reply burned ~208k tokens). Until it's fixed, teammates don't start subagents. If you're a teammate, do the hands-on work yourself, drive workers through herdr (no subagent needed), or ask the main session to start Claude subagents and relay the results. If you're a main session, start workers and reviewers yourself and pass results to your teammate.
- Final results truncate at about 4,000 characters. For long reports, ask for SendMessage parts of 3,500 characters or less, or use `schema`.
- `isolation: "worktree"` is unreliable: every Bash call in the agent can fail with "The working-directory isolation context for this agent was lost…" and the worktree gets removed. Seen on 2026-09-29 (session launched outside a git repo) and 2026-10-02 (inside a git repo, background agent); EnterWorktree inside the agent doesn't help. Until it's fixed: create the worktree yourself (`git -C <repo> worktree add <path> -b <branch>`), spawn the agent WITHOUT `isolation`, tell it to work only in that absolute path, and remove the worktree when done.
- Never SendMessage an agent that is still running inside a Workflow, even if its id appears in a `from=` attribute: the reply starts a second copy of the agent while the first keeps running, and both write the same worktree. Wait for it to finish, or edit the script and rerun with `resumeFromRunId`.
- An Agent call with a `name` becomes a teammate. Its completion notice often never arrives, and reports it sends to `team-lead` (the name Claude Code gives it for you) are dropped; reports to `main` arrive. Seen in four sessions, 2026-10-27/29. For one-off research, omit `name`. For a named agent, tell it in the brief to report with SendMessage to `main`. If one goes idle without reporting, message it by name for the report, or read its transcript under ~/.claude/projects/<project>/<session>/subagents/.

## Auto mode
- When the classifier denies an action, don't route around it: no renaming, other paths, splitting, heredocs or reworded retries. Bring the exact command to the user.
- The user's approval in your conversation doesn't reach your subagents: each is judged on its own brief. Seen three times on 2026-10-28 ("Production Reads", "Excess Sensitive Detail"). Run a user-approved sensitive step in the main session, with the user switching it out of Auto mode for that step (Shift+Tab) and approving the prompt, or have the user run it with `! <command>`.
- UAT and other non-production reads (e.g. `kubectl exec`, credential-backed calls) can still be denied as "Production Reads"; handle them the same way.

## Shell pitfalls
- A global kill guard blocks pattern kills (`pkill -f`, `pkill` without `-x`, `killall -m`, `pgrep <pattern> | xargs kill`, `kill -1`/`kill 0`); `pkill -f "cat"` once killed 37 of the user's apps. Kill by recorded PID (`$!`, a pidfile you wrote from `$!`) or port owner (`lsof -ti :PORT -sTCP:LISTEN`; without `-sTCP:LISTEN` it also returns clients such as the user's browser). Use the port-owner form only for a process you started on that port yourself: if your own bind or forward fails, the port belongs to someone else (often another session's SSH forward), so stop there; never write lsof/ps results into your pidfile or kill them. On 2026-11-02 a teammate did exactly that and killed the digital-portal session's mac-stack forward. If a hung `cat`/`tail` is blocking you, find its PID with `pgrep -lx cat` and kill only that PID.
- The dotfiles skip the eza/bat/fd aliases when `CLAUDECODE` is set, so `ls`, `cat` and `find` are the plain commands.
- A Bash `timeout` doesn't stop the command. After about 600 s (the cap; larger values aren't enforced as written) Claude Code hands control back and the command keeps running in the background, holding CPU, slots and locks; in a background teammate a call once blocked for over 10 hours (2026-10-24/25). Keep `timeout` at 600000 or below, and give long or heavy commands their own deadline: a wrapper that kills its process group, like digital-portal's `.tools/run-limited.sh`. macOS has no `timeout` binary.

## The shared container host
- The VM is garage-server's rootless `podman-machine-default` (arm64). The Linux workstation is retired.
- The rpa Steel stack's deploys refuse while a browser is busy.
- Changes to the VM or its runtime (`podman machine set`/`stop`/`start`, Podman upgrades on garage-server, `containers.conf`/registries changes) need the user's go first, then an announcement to claude-config.
- `podman login` on garage-hq stores credentials in garage-hq's ~/.config/containers/auth.json. If a push can't reach a registry from garage-server (e.g. a LAN-only registry like PCS Harbor), report it.
- Never create a Podman volume with `--opt type=none`/`o=bind` on a directory you didn't create for the purpose (above all anything under `/Users`, `/private` or `/var/folders` — garage-server's real files, through virtiofs), and never `podman volume rm` such a volume after a mount error: rootless Podman can leave the bind mounted, and the rm then deletes the source directory's contents through it (on 2026-10-31 this wiped `/run/user/1000` on the old workstation). Test volume options on a scratch directory under your own work dir.
