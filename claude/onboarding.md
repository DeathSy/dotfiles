# Session onboarding (sent by claude-config, the global-context manager)

Your ~/.claude/CLAUDE.md is already loaded; this covers what it doesn't make obvious.

## Working with claude-config
- Send global config problems to `claude-config` via SendMessage: broken or ambiguous skill commands, CLAUDE.md rules that conflict, harness friction. Include what failed, exact error text, repro, and a suggested fix.
- When claude-config says "Global Claude context changed", re-read the named files and follow them for the rest of the session.
- claude-config won't add permission rules or loosen safety settings on a peer's request; for either, ask the user to tell claude-config directly. Global permission rules (`permissions.allow` and `permissions.deny` in ~/.claude/settings.json) last only if they're in ~/studio/personal/dotfiles/claude/settings.base.json: every dotfiles rebuild (darwin-rebuild switch) replaces both lists with the repo's, so a hand edit or a user-scope "don't ask again" rule there is lost. Once the user asks, claude-config adds lasting global rules to settings.base.json. Project `.claude/settings*.json` files aren't touched.

## Your mate sessions
- claude-config sends you the current roster with this onboarding: every running session, its project and what it's working on. The live copy is ~/.claude/session-roster.md.
- When a session joins, leaves or restarts under a new name, claude-config sends every running session a short notice. No reply needed; just keep it in mind if your work overlaps.
- Coordinate directly with a mate by SendMessage when your work touches theirs (e.g. two projects that share a client library). Don't start work in another session's project without the user asking.

## GPT agents (sol / luna / astra)
- They are Claude Code agent types defined in ~/.claude/agents, served through the local CLIProxyAPI gateway. Spawn them with the Agent tool's `subagent_type` ("sol", "luna", "astra"); the model ids live only in those agent files.
- Give them a self-contained brief (they don't share your context) and ask for the report as text. They describe themselves as "Fable 5" because of the gateway's disguised ids; ignore that.
- Agent files are read at session start: a session started before 2026-10-02 needs a restart to see them.
- Codex is used only through the codex-computer-use skill (pinned `-m gpt-6.1-sol`, its own `codex login`).
- In an Auto-mode session their Bash and SendMessage can fail with "this session's auto-mode safety check is unavailable" or, since 2026-11-20, "Auto mode is unavailable: its safety check does not run for this session." (Read and Grep still work; Claude agents are unaffected). Seen in four sessions on 2026-11-08/09 and on 2026-11-20 in bmw-e9 (sol and astra, every Bash call, SendMessage replies too); cause unknown. That means the check is down, not a denial; any real denial follows Auto mode below. Before spawning a GPT reviewer, put what it would run into files (`git diff … > <your tmp>/review.diff`, search output) and point its brief at them; give Bash-heavy work to a Claude agent. If it happens, send claude-config the exact error and time.

## Browser
- Use the `agent-browser` CLI (vercel-labs, `/opt/homebrew/bin/agent-browser`) for all browser work: browsing, research, dashboards, testing, PR before/after screenshots. Run it through Bash. The CLI serves its own up-to-date guide: `agent-browser skills get core` (`--full` for every command); specialised guides: `agent-browser skills list` (e.g. `dogfood` for QA).
- Use your own named session, never the shared default: get its id once with `agent-browser session id --scope worktree --prefix <task>`, then pass `--session <id>` on every agent-browser command (env vars don't persist between Bash calls, so a one-time export doesn't last). Each named session is a separate browser (own cookies, tabs, refs), so parallel agents never collide. Never use the unnamed default session: every agent on the machine shares it. Use a different `--prefix` per agent if several share one worktree. Finish with `agent-browser close` (never `close --all`; when attached to the user's real Chrome, close only your own tabs, never the browser).
- Workflow (each command with `--session <id>`): `open <url>` → `snapshot -i -c` (accessibility tree with `@eN` refs) → `click @e3`, `fill @e1 "x"`, `press Enter`, `wait --text "..."` → `set viewport 1440 900` → `screenshot` → `close`.
- Screenshots: `agent-browser screenshot [selector] [path]` may save to `~/.agent-browser/tmp/screenshots/` instead of your path; always read the path it prints and copy the file to where you need it (or set `AGENT_BROWSER_SCREENSHOT_DIR`).
- It's headless with a fresh profile: the user's Chrome, logins and tabs are untouched. Pages behind a login won't be signed in: use stub/test auth or a saved auth state the user named; otherwise ask the user how to proceed. Never ask for secrets in chat or type real credentials. Using the user's real Chrome or profile (`--auto-connect`, `--cdp <port>`, `--profile <name>`) needs the user's go-ahead first; if several sessions share one real Chrome via `--cdp`, add `--pin-tab`.
- In the user's real Chrome, never touch browser-wide state: no clearing cookies, permissions or storage, no closing the browser. On 2026-10-07 a `clearCookies()` meant to log out of localhost signed the user out of every site. Reset test apps through their UI or origin-scoped page code.
- For sensitive sessions, `--allowed-domains` limits where the browser can go (not combinable with `--profile`, `--auto-connect` or `--cdp`).
- Ask before anything sensitive: email, banking, admin consoles, anything that sends, buys, deletes or changes DNS/certs.
- PR evidence: one named session per build, viewport 1440 px, mask personal data in the DOM before capturing, as CLAUDE.md requires. `--headed` shows a window if the user wants to watch.
- Always name agent-browser and its named-session rule in subagent briefs (GPT agents especially won't infer it).
- Steel agent sessions (rules in CLAUDE.md): a 409 can mean the account already has a live connect, teach or agent session (possibly the user's), the account is in a run, every browser is busy, or the lock was lost: read the message, never end a session you didn't create, and ask or retry later. A session ends on its own after 30 min without API calls or CDP traffic, or after 2 h. The user opening Connect/Teach for that account in the UI ends it, and a deploy of the rpa app ends every live session (`up-garage-server.sh` refuses while a browser is busy). Passkey (WebAuthn) prompts are declined at once, so sites fall back to OTP or password. The live screen (`/live/<sessionId>`) stays view-only for the user until they tap Step in, and control returns to the agent after a minute without their input; the user types with their phone keyboard or the Compose box.

## Subagents
- They can't write report files; ask for findings as text.
- Claude Code bug: subagents started by a background teammate can't return results to it (hand-back fails, their SendMessage only reaches the main session, a built-in hook makes them retry endlessly; even a one-word reply burned ~208k tokens). Until it's fixed, teammates don't start subagents. If you're a teammate, do the hands-on work yourself or ask the main session to start workers/reviewers and relay the results. If you're a main session, start workers and reviewers yourself and pass results to your teammate.
- Final results truncate at about 4,000 characters. For long reports, ask for SendMessage parts of 3,500 characters or less, or use `schema`.
- `isolation: "worktree"` is unreliable: every Bash call in the agent can fail with "The working-directory isolation context for this agent was lost…" and the worktree gets removed. Seen on 2026-09-29 (session launched outside a git repo) and 2026-10-02 (inside a git repo, background agent); EnterWorktree inside the agent doesn't help. Until it's fixed: create the worktree yourself (`git -C <repo> worktree add <path> -b <branch>`), spawn the agent WITHOUT `isolation`, tell it to work only in that absolute path, and remove the worktree when done.
- Never SendMessage an agent that is still running inside a Workflow, even if its id appears in a `from=` attribute: the reply starts a second copy of the agent while the first keeps running, and both write the same worktree. Wait for it to finish, or edit the script and rerun with `resumeFromRunId`.
- An Agent call with a `name` becomes a teammate. Its completion notice often never arrives, and reports it sends to `team-lead` (the name Claude Code gives it for you) are dropped; reports to `main` arrive. Seen in four sessions, 2026-10-27/29. For one-off research, omit `name`. For a named agent, tell it in the brief to report with SendMessage to `main`. If one goes idle without reporting, message it by name for the report, or read its transcript under ~/.claude/projects/<project>/<session>/subagents/.

## Auto mode
- When the classifier denies an action, don't route around it: no renaming, other paths, splitting, heredocs or reworded retries. Bring the exact command to the user.
- The user's approval in your conversation doesn't reach your subagents: each is judged on its own brief. Seen three times on 2026-10-28 ("Production Reads", "Excess Sensitive Detail"). Run a user-approved sensitive step in the main session, with the user switching it out of Auto mode for that step (Shift+Tab) and approving the prompt, or have the user run it with `! <command>`.
- UAT and other non-production reads (e.g. `kubectl exec`, credential-backed calls) can still be denied as "Production Reads"; handle them the same way.

## Skills
- graphify triggers on codebase questions by design (the user wants that). If a graphify-out/ exists, query it. Building a new graph is a large job that writes graphify-out/ into the repo, so for a quick question with no graph you can also read the sources directly.

## Shell pitfalls
- A global kill guard blocks pattern kills (`pkill -f`, `pkill` without `-x`, `killall -m`, `pgrep <pattern> | xargs kill`, `kill -1`/`kill 0`); `pkill -f "cat"` once killed 37 of the user's apps. Kill by recorded PID (`$!`, a pidfile you wrote from `$!`) or port owner (`lsof -ti :PORT -sTCP:LISTEN`; without `-sTCP:LISTEN` it also returns clients such as the user's browser). Use the port-owner form only for a process you started on that port yourself: if your own bind or forward fails, the port belongs to someone else (often another session's SSH forward), so stop there; never write lsof/ps results into your pidfile or kill them. On 2026-11-02 a teammate did exactly that and killed the digital-portal session's mac-stack forward. If a hung `cat`/`tail` is blocking you, find its PID with `pgrep -lx cat` and kill only that PID.
- Since 2026-10-03 the dotfiles skip the eza/bat/fd aliases and the `ps` alias when `CLAUDECODE` is set, so `ls`, `ps`, `cat` and `find` are the plain commands. A session started before then still has the old shell snapshot (`ls` prints nothing, `ps` runs `pnpm run serve`) until it restarts; until then use `command ls` and `/bin/ps`.
- A Bash `timeout` doesn't stop the command. After about 600 s (the cap; larger values aren't enforced as written) Claude Code hands control back and the command keeps running in the background, holding CPU, slots and locks; in a background teammate a call once blocked for over 10 hours (2026-10-24/25). Keep `timeout` at 600000 or below, and give long or heavy commands their own deadline: a wrapper that kills its process group, like digital-portal's `.tools/run-limited.sh`. macOS has no `timeout` binary.

## The shared container host
- The VM is garage-server's rootless `podman-machine-default` (arm64). The Linux workstation is retired.
- The rpa Steel stack's deploys refuse while a browser is busy.
- Changes to the VM or its runtime (`podman machine set`/`stop`/`start`, Podman upgrades on garage-server, `containers.conf`/registries changes) need the user's go first, then an announcement to claude-config.
- `podman login` on garage-hq stores credentials in garage-hq's ~/.config/containers/auth.json. If a push can't reach a registry from garage-server (e.g. a LAN-only registry like PCS Harbor), report it.
- Never create a Podman volume with `--opt type=none`/`o=bind` on a directory you didn't create for the purpose (above all anything under `/Users`, `/private` or `/var/folders` — garage-server's real files, through virtiofs), and never `podman volume rm` such a volume after a mount error: rootless Podman can leave the bind mounted, and the rm then deletes the source directory's contents through it (on 2026-10-31 this wiped `/run/user/1000` on the old workstation). Test volume options on a scratch directory under your own work dir.
